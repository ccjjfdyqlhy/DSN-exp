# v1.0.0

The first release you can actually install and use.

Everything before this one shipped to PyPI successfully and was **broken for
the people who installed it**: `pip install aicf-core` resolved to `0.6.2`
(the release candidates are pre-releases, and pip does not install those by
default), and that wheel had neither a `console_scripts` entry point nor the
packaged evaluation dataset. So `aicf --version`, `aicf tool list`,
`aicf eval --dataset basic` — every command in the README's "ninety seconds" —
failed with *command not found*. The source tree was green the whole time,
because CI tests the source, and the users install the wheel. That gap is
closed now.

## Breaking: one namespace

`harness` and `infra` are both **already taken on PyPI**. A library that
installs those names into your `site-packages` is a library that breaks other
people's environments. Both layers now live under one top-level package:

| Before (≤ 1.0.0rc3) | Now |
|---|---|
| `from harness import create_agent` | `from aicf.harness import create_agent` |
| `from harness.tools import ToolRegistry` | `from aicf.harness.tools import ToolRegistry` |
| `from infra.models.base import IChatClient` | `from aicf.infra.models.base import IChatClient` |

`from aicf import create_agent` works too — the same symbol, forwarded lazily
(PEP 562), so `import aicf` stays cheap.

The distribution name (`aicf-core`) and the CLI (`aicf`) are unchanged. They
cannot be the same string: PyPI rejects a project name that is too similar to
an existing one, so `aicf` was never available as a distribution name — but it
was available as an import name, and that is where the collision actually hurt.

## The gate that keeps this from happening again

`scripts/wheel_smoke.py` builds the wheel, installs it into a **fresh virtual
environment**, and then uses it the way the README says:

- the wheel's top-level packages are exactly `aicf` (no squatting);
- `console_scripts` declares `aicf`;
- the evaluation dataset ships inside the package;
- the installed version matches the declared version;
- `aicf --version` and `aicf tool list` run;
- `aicf eval --dataset basic` reads the packaged dataset;
- `from aicf.harness import create_agent, tool` imports.

It runs in `ci.yml` on every push and in `release.yml` **before** the publish
step. The 0.6.2 wheel, fed to it, turns every static check red.

## What was already in the release candidates

The three claims this project set out to make hold on the default paths, and
each one is pinned to a test:

1. an agent that is `kill -9`'d once still resumes and produces the right
   answer — `pytest tests/fault/`;
2. every tool call was either approved or refused, with an audit trail in a
   store the business cannot delete;
3. the run can be scored against the dataset and produces a four-gate report
   that blocks a release on regression, cost overrun or a rule violation.

The release candidates also delivered the control plane (agent artifacts,
lifecycle, cost ledger), the workflow and planner kernels, agent identity and
delegation, the online sampling and bad-case loop, the scheduler with
workspace isolation, the tool discovery and the policy loader, and the
grounding and memory layers. See
[rc3](v1.0.0rc3.md) · [rc2](v1.0.0rc2.md) · [rc0](v1.0.0rc0.md).
