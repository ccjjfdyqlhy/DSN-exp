aicf-core · Apache-2.0 · Python 3.10+ · local-first

假设进程活不下来的
Agent 运行时。

一句话承诺：安全跑完一次长任务——每个工具调用过策略闸门， 崩溃后能恢复且不重复副作用，每次运行都留下可打分的 trace。

$ pip install aicf-core

本仓只含两层库：aicf/harness（Agent 核心）与 aicf/infra（模型、资源、存储、策略）。 Web 控制台在独立仓库 aicf-ui。

  • Safe策略闸门 · 人审批 · 沙箱 · 未决即拒绝
  • Idempotentkill -9 可恢复 · 副作用不重放
  • Measurabletrace → dataset 打分 → 四闸门报告

三条承诺，怎么自己验

不需要相信文档。三条承诺都有对应的命令或测试，跑一遍就知道真假。

承诺 它到底保证了什么 怎么自己验
Safe 每个工具调用都过策略闸门；有副作用的工具需要人批准； 在沙箱内执行；未决即拒绝（deny-by-default）。 
aicf tool exec proc.run \
  --args '{"command":"rm -rf /"}' \
  --policy strict

→ 被策略拒绝，退出码非 0；审批悬置同样算拒绝。
Idempotent 进程被 kill -9 之后能恢复，并且不会重复已发生的副作用； effectful 调用不会自动重放。Journal 是真相，checkpoint 只是加速器。 
pytest tests/fault/

→ 在子进程里真的 kill -9，再从 journal 恢复；aicf session resume 继续未完成的轮次。
Measurable 每次运行产出 trace；能对数据集打分； 四闸门报告拦住回归、成本超标或规则破坏。 
aicf run "..." --trace trace.jsonl
aicf eval --dataset basic \
  --traces trace.jsonl --out run.json
aicf gate --run run.json --out gate.json

→ 四道闸门：质量 / 回归 / 成本 / 安全。任一不过即阻断发布；安全闸门零容忍。

90 秒上手

下面五条命令不需要任何 API key——它们跑在内置的离线 stub 模型上。

  1. 01

    装上

    pip install aicf-core

    分发名 aicf-core，命令入口 aicf，import 名 aicf.*。

  2. 02

    看工具目录：副作用等级、沙箱档位、所需授权范围

    aicf tool list

    先知道每个工具能干什么，再决定让 agent 用哪些。

  3. 03

    试一次会被拒绝的调用

    aicf tool exec proc.run --args '{"command":"rm -rf /"}' --policy strict

    → Error: 工具 proc.run 被策略拒绝（approval）：CLI 未开启 --yes 有副作用的工具不会自己跑起来。

  4. 04

    跑一轮，留下一份 trace

    aicf run "summarize this repo" --trace trace.jsonl

    trace 是 JSONL，一行一个事件——后面的打分靠它。

  5. 05

    打分，然后出四闸门报告

    aicf eval --dataset basic --traces trace.jsonl --out run.json
aicf gate --run run.json --out gate.json

    数据集 basic 随包发布。gate.json 里有四道闸门的逐项判定—— 质量、回归、成本、安全。发布前先看这份报告。

Python 快速上手

三个符号：tool、create_agent、Agent。 任何 OpenAI 兼容端点都能接；本地模型就把 base_url 指向 llama-server / LM Studio。 

from aicf.harness import create_agent, tool

@tool
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b

agent = create_agent(
    model="deepseek-chat",
    base_url="https://api.deepseek.com/v1",
    api_key="sk-...",                 # 或者直接 export OPENAI_API_KEY
    tools=[add],
)

print(agent.run("what is 17 + 25?"))

常用导入

from aicf.harness import create_agent, tool, Agent
from aicf.harness.tools import ToolRegistry
from aicf.infra.models.base import IChatClient

自己管工具表时用 ToolRegistry；接自己的后端时实现 IChatClient。

离线也能跑

aicf run "hello" --trace trace.jsonl
aicf eval --dataset basic \
  --traces trace.jsonl --out run.json

不配 API key 时 CLI 走内置 stub 模型，评测闭环照样跑得通。

架构：两层，依赖只向下

本仓库只有这两层。放代码前先回答一个问题：它关心业务语义，还是只管资源？

aicf/harness Agent 核心层

只处理「消息进、工具出」：轮次循环、工具协议与注册表、上下文装配与裁剪、 记忆、会话与 transcript、管线与事件。不认识任何业务。

  • agent loop
  • tools
  • context assembly
  • memory
  • sessions
  • pipeline / events
依赖只向下 ↓ harness 只通过 Protocol 依赖 infra：契约（ToolSpec / PolicyEngine / ApprovalBroker / Sandbox / TelemetryPort / RuntimeClient）住在 harness，实现在 infra，由应用装配时注入。
aicf/infra 资源与基础设施层

只管进程、HTTP、显存、磁盘、密钥与预算：模型路由、资源池、存储、网关、认证、策略。 不知道业务语义。

  • model routing
  • resource pool
  • storage
  • gateway
  • auth
  • policy

规则一：依赖只向下

认业务 → 属于 aicf-ui 仓库；关心消息与工具 → aicf/harness；只管进程/HTTP/显存/磁盘/密钥 → aicf/infra。

规则二：infra/eval 与 infra/runtime 不得 import harness

评测层只认自己定义的 Trace / ToolCall，由 trace_from_events() 做只读适配。

规则三：未判定 ≠ 通过

没有 baseline 时，回归与成本闸门明确标「未判定」，不会默默给一个 PASS。

迁移到 1.0.0

1.0.0 起顶层不再占用 harness 与 infra 这两个名字， 全部收进 aicf 命名空间。分发名与命令行入口都不变。

旧（<= 0.6.x） 新（1.0.0+）
from harness import create_agent, tool → from aicf.harness import create_agent, tool
from harness.tools import ToolRegistry → from aicf.harness.tools import ToolRegistry
from infra.models.base import IChatClient → from aicf.infra.models.base import IChatClient
from infra.x import y → from aicf.infra.x import y

一条命令扫出所有待改的导入

grep -rn --include='*.py' \
  -E '(^|\s)(from|import)\s+(harness|infra)\b' .

顶层名字不再被占用，因此不会和别的项目里的 harness / infra 撞车。

不变的三个东西

  • 安装名：pip install aicf-core
  • 命令入口：aicf
  • 仓库地址：github.com/ccjjfdyqlhy/aicf-core

只有 Python 里的 import 路径变了，配置文件与命令行参数不受影响。
